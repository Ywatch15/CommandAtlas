## What is it?

`docker load` is a command-line utility used to read a tar archive file (typically generated by `docker save`) and import its packaged Docker images, filesystem layers, and metadata back into the local Docker daemon's storage cache. It perfectly restores serialized images so they can be executed identically on a disconnected machine.

## Why does it exist?

When deploying containerized applications into highly secure, disconnected, or air-gapped environments where running `docker pull` against an external internet registry is impossible, administrators must transfer images physically. `docker load` exists as the restorative counterpart to `docker save`. It parses incoming physical archive files, decompresses layers, and reintegrates them into the Docker daemon, enabling seamless offline software delivery.

## Syntax

```bash
docker load [OPTIONS]
```

## Flags

| Flag                     | Description                                                                                              | Example                            |
| ------------------------ | -------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `-i`, `--input <string>` | Specifies the file path of the tar archive to read from, instead of reading from standard input (STDIN). | `docker load -i ubuntu_backup.tar` |
| `-q`, `--quiet`          | Suppresses the verbose progress output bar that typically tracks layer restoration.                      | `docker load -q -i app.tar.gz`     |
| `--help`                 | Outputs brief usage documentation and supported command-line options.                                    | `docker load --help`               |

## Examples

```bash
docker load -i nginx-backup.tar
```

> This explicitly reads the `nginx-backup.tar` file from the local disk, unpacks its internal layer structures, and restores the image(s) into the local Docker daemon cache, preserving all original tags.

```bash
docker load < busybox.tar.gz
```

> This utilizes bash standard input redirection (`<`) to stream the contents of a compressed archive directly into `docker load`. The Docker daemon natively detects and handles decompression formats like gzip, bzip2, and xz automatically.

```bash
cat bundled-app.tar | docker load
```

> This pipes the raw byte stream of an uncompressed tarball directly into the `docker load` command. This is highly useful when transferring images over SSH streams where the file never touches the target machine's disk.

```bash
docker load -q -i massive-image.tar
```

> This loads a massive image archive while suppressing the multi-line progress rendering (`-q`), keeping automated CI/CD logs clean and readable by only printing the final restored image IDs.

## Real-World Scenarios

**Air-Gapped Infrastructure Provisioning**

```bash
sudo docker load -i /mnt/usb_drive/security-app.tar.gz
```

> Systems administrators operating classified, disconnected military or financial networks mount secure USB drives containing approved software updates and use `docker load` to ingest the container images into isolated host machines.

**Rapid CI/CD Node Pre-Warming**

```bash
aws s3 cp s3://ci-cache/base-image.tar.zst - | zstd -d | docker load
```

> To bypass slow network registry throttling during massive parallel testing, CI pipelines stream heavily compressed foundational base images from object storage buckets, decompressing and loading them into memory on the fly to accelerate runner boot times.

**Zero-Registry Edge Device Deployment**

```bash
ssh root@iot-device "docker load" < ./smart-hub-v2.tar
```

> IoT engineers pushing firmware updates to remote, low-bandwidth edge devices (like Raspberry Pis on 4G networks) stream serialized Docker images directly over SSH tunnels into the remote `docker load` process, bypassing the need to host and maintain a private registry for the devices.

## When should it NOT be used?

- **Loading raw container filesystems created via `docker export`:** **Reason:** `docker load` specifically expects the structured, multi-layer, metadata-rich archives generated by `docker save`. Archives from `docker export` lack metadata and will fail to load. **Use instead:** `docker import`.
- **Distributing images over fast, connected networks:** **Reason:** Loading entire tarballs requires heavy local disk I/O to extract and process. **Use instead:** `docker pull` from a registry, which is natively optimized for concurrent chunk downloading and layer deduplication.

## Alternatives

- **`docker pull`:** Network-based registry retrieval. **Tradeoff:** Requires active network connections and registry authorization, but is far more efficient for iterative updates than transferring monolithic tarballs.
- **`docker import`:** Container filesystem import. **Tradeoff:** Used specifically to import flattened, raw filesystem tarballs (from `docker export` or manual creation) as a single-layer image without metadata, rather than restoring a full multi-layer Docker image.

## How it works internally

When you execute `docker load`, the CLI opens the specified file (or listens to STDIN) and initiates an HTTP `POST /images/load` request to the local Docker daemon.

The daemon begins streaming the tar archive into memory. It natively detects common compression headers (gzip, bzip2, xz) and decompresses the stream on the fly if necessary. It reads the internal `manifest.json` embedded in the archive to understand the layer structure and image tags.

For each layer tarball found inside the archive, the daemon checks if a layer with a matching SHA-256 hash already exists in the local Graph/OverlayFS storage. If it exists, the daemon skips it, preserving disk I/O. If missing, it extracts the layer to disk. Finally, the daemon reconstructs the image configuration metadata and applies the repository and tag aliases to its internal database, making the image visible to `docker images`.

## Performance Notes

- Loading multi-gigabyte uncompressed tar archives generates massive sequential disk writes as the daemon extracts internal layers into the storage driver path (`/var/lib/docker`). Slow magnetic hard drives (HDDs) will severely bottleneck this process.
- Piping compressed streams (e.g., `< image.tar.gz`) shifts the decompression workload to the Docker daemon process, consuming moderate CPU overhead but drastically reducing disk read I/O.

## Security Notes

- **Malicious Archive Processing:** `docker load` processes untrusted tar archives as a privileged root daemon. Loading tampered tar files theoretically exposes the daemon to directory traversal or decompression bomb vulnerabilities (though Docker includes mitigations). Only load archives from trusted sources.
- **No Native Integrity Checks:** The `docker load` command does not natively verify cryptographic signatures or external checksums before unpacking. Always verify the SHA-256 hash of the `.tar` file manually before feeding it to `docker load` on classified systems.

## Common Mistakes

- **Confusing `load` with `import`:** Trying to run `docker load -i exported-container.tar`. **Why it's wrong:** If a tarball was created using `docker export` (which dumps a raw filesystem), `docker load` will crash because it expects the strict `manifest.json` structure created by `docker save`. You must use `docker import` instead.
- **Forgetting shell redirection syntax:** Running `docker load file.tar`. **Why it's wrong:** The CLI expects either the `-i` flag or data piped via standard input. Passing the filename as a raw argument causes a syntax error.
- **Assuming load forces container restart:** **Why it's wrong:** `docker load` strictly restores the static image blueprint into the cache. If a container based on a previous version of that image is actively running, it will continue running the old code until it is explicitly deleted and recreated.

## Best Practices

- Use standard input redirection (`docker load < archive.tar.gz`) instead of the `-i` flag when possible, as it allows the shell to handle complex compressed streams dynamically without requiring manual decompression tools.
- When deploying updates to isolated environments via sneakernet (USB drives), always bundle the `.tar` archive alongside a cryptographic checksum file (e.g., `.sha256`) and verify it locally before executing the load operation to guarantee integrity.

## Interview Questions

- _Query:_ What is the fundamental difference in expected input between `docker load` and `docker import`?
  - _A:_ `docker load` specifically expects a structured archive generated by `docker save`, containing multiple layers, image history, and execution metadata (JSON manifests). `docker import` expects a flat, raw filesystem archive (typically generated by `docker export` or `tar`), and creates a single-layer image completely devoid of historical metadata.
- _Query:_ If you run `docker load` using a tarball that contains an image with a specific tag (e.g., `app:v1`), and an image with that exact tag already exists on your host, what happens?
  - _A:_ The Docker daemon will process the archive, extract the layers, and forcibly update the `app:v1` tag pointer to point to the newly loaded image ID. The previous image that held that tag will become untagged (a dangling image marked as `<none>:<none>`).
- _Query:_ Does `docker load` natively support unpacking compressed tar archives (like `.tar.gz`)?
  - _A:_ Yes. If you pass a compressed archive (gzip, bzip2, xz) using the `-i` flag or standard input redirection, the Docker daemon automatically detects the compression header and decompresses the stream on the fly before processing the internal layers.

## Practice Problems

- _Problem:_ Import a saved image archive located at `/tmp/redis-backup.tar` into your local Docker cache using the explicit input flag.
  - _Hint:_ Use the load command paired with the input flag specifying the absolute path.
  - _Solution:_ `docker load -i /tmp/redis-backup.tar` (This instructs the CLI to read the file path directly and transmit it to the daemon).
- _Problem:_ Stream a gzip-compressed archive named `custom-alpine.tar.gz` directly into the `docker load` utility using shell standard input redirection.
  - _Hint:_ Use the shell's `<` redirection operator rather than Docker's `-i` flag.
  - _Solution:_ `docker load < custom-alpine.tar.gz` (The shell streams the binary data to Docker's standard input, where the daemon automatically decompresses and loads it).
