## What is it?

`patch` is a classic UNIX command-line utility that takes a file containing a list of differences (a "diff" file) and intelligently applies those changes to the original files. It interprets context and unified diff formats, modifying text files in-place by adding, modifying, or deleting lines according to the instructions generated by the `diff` command.

## Why does it exist?

Before the advent of decentralized version control systems like Git, distributing entire codebases for every minor bug fix over slow dial-up modems was impossible. Larry Wall created `patch` in 1985 to allow developers to distribute only the _changes_ (deltas) made to a codebase. It exists to provide a mathematically resilient way to merge code updates across disparate environments, utilizing context lines to accurately apply changes even if the target file has been slightly modified since the patch was created.

## Syntax

```bash
patch [options] [originalfile [patchfile]]
patch -p<num> < patchfile
```

## Flags

| Flag                          | Description                                                                                                | Example                           |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------- |
| `-p<num>`, `--strip=<num>`    | Strips the smallest prefix containing `num` leading slashes from each file name found in the patch.        | `patch -p1 < fix.diff`            |
| `-i <file>`, `--input=<file>` | Explicitly reads the patch from the specified file instead of standard input.                              | `patch -i fix.patch`              |
| `-R`, `--reverse`             | Assumes the patch was created with the old and new files swapped, essentially undoing/reversing the patch. | `patch -R -p1 < fix.diff`         |
| `--dry-run`                   | Prints the results of applying the patch without actually modifying any files on disk.                     | `patch --dry-run -p1 < a.patch`   |
| `-b`, `--backup`              | Saves a backup copy of the original file (usually appending `.orig`) before modifying it.                  | `patch -b config.c`               |
| `-d <dir>`, `--directory`     | Changes the working directory to the specified path immediately before applying the patch.                 | `patch -d /opt/src -p1 < x.patch` |
| `-u`, `--unified`             | Forces the parser to interpret the patch file as a Unified Context Diff.                                   | `patch -u < patch.diff`           |
| `-F <num>`, `--fuzz=<num>`    | Sets the maximum "fuzz" factor (context lines that can be ignored if they don't match).                    | `patch -F 2 < dirty.patch`        |
| `-E`, `--remove-empty-files`  | Automatically deletes target files if the patch completely empties them of all content.                    | `patch -E -p1 < cleanup.diff`     |
| `-f`, `--force`               | Suppresses all interactive prompts, assuming the user knows exactly what they are doing.                   | `patch -f < automated.patch`      |

## Examples

```bash
patch -p1 < kernel_update.patch
```

> This is the definitive canonical usage. It reads the unified diff from standard input and applies it. The `-p1` flag instructs the engine to strip the first directory level from the filenames embedded in the patch (e.g., converting `a/src/main.c` to `src/main.c`), which is the standard format generated by `git diff`.

```bash
patch --dry-run -p1 < risky_change.diff
```

> This invokes a simulation. The utility parses the patch, calculates line offsets, evaluates context fuzz, and outputs exactly which "hunks" would succeed or fail (creating `.rej` files in memory), but exits without touching the physical files on disk.

```bash
patch -R -p1 < bad_commit.patch
```

> This performs a mathematical rollback. If a patch introduced a catastrophic bug, supplying the exact same patch file to `patch -R` instructs the engine to invert the add/delete instructions, stripping the new code and restoring the original lines perfectly.

```bash
patch -b -p0 < /tmp/hotfix.diff
```

> This applies a patch using absolute file paths (`-p0` strips zero directories) while enforcing a strict safety net. The `-b` flag forces `patch` to duplicate the target file (creating `filename.orig`) before mutating it, allowing rapid manual restoration if the compilation fails.

```bash
diff -u old.py new.py | patch -d /production/app -p0
```

> This leverages the pipeline for instant remote deployment. It generates a unified diff (`-u`) on the fly from two local files, pipes the delta stream directly into `patch`, which shifts its execution context to `/production/app` (`-d`) and applies the mutation.

## Real-World Scenarios

**Applying Source-Code Security Backports**

```bash
wget [https://security.kernel.org/cve-2026-1234.patch](https://security.kernel.org/cve-2026-1234.patch)
patch -d /usr/src/linux -p1 --dry-run < cve-2026-1234.patch
patch -d /usr/src/linux -p1 < cve-2026-1234.patch
```

> Systems administrators maintaining heavily customized, legacy Linux kernels cannot simply execute `git pull`. They download raw `.patch` files containing critical CVE fixes, perform a dry run to ensure their custom code hasn't skewed the context lines beyond the fuzz limit, and apply the surgical fix manually.

**Hot-Fixing Containerized Applications**

```bash
kubectl exec -it web-pod-123 -- sh -c "patch -p1 < /mnt/shared/hotfix.diff"
```

> DevOps engineers dealing with a critical production outage in a legacy application inject a `patch` file via a shared volume. They execute `patch` inside the running container to mutate the raw Python or PHP source files in-memory without waiting for a 30-minute CI/CD pipeline container rebuild.

## When should it NOT be used?

- **Applying commits inside a Git repository:** **Reason:** `patch` is completely unaware of Git's index, staging area, or SHA-1 hashes. It modifies the working directory blindly. **Use instead:** `git apply` (modifies working tree) or `git am` (applies patches as full Git commits with author data).
- **Modifying compiled binaries or proprietary formats:** **Reason:** `patch` strictly manipulates plaintext files line-by-line using newline delimiters. Attempting to `patch` an `.exe` or `.pdf` will hopelessly corrupt the binary payload. **Use instead:** Binary delta tools like `bsdiff` and `bspatch`.

## Alternatives

- **`git apply`:** The modern Git integration. **Tradeoff:** It is significantly faster and natively understands Git metadata, binary patches, and renames, but explicitly requires a Git repository structure to function optimally.
- **`sed -i`:** Stream editing. **Tradeoff:** `sed` blindly executes regex substitutions without verifying surrounding context. `patch` mathematically guarantees that the lines above and below the change match the original author's intent, making it infinitely safer for code modification.

## How it works internally

`patch` operates by parsing instructions called "hunks" within a unified or context diff file.

A unified diff specifies the target file and then provides blocks of code (hunks) prefixed with metadata like `@@ -15,7 +15,8 @@`. This tells `patch` that the original code started at line 15 and was 7 lines long, and the new code should start at line 15 and be 8 lines long.

When `patch` processes a hunk, it doesn't blindly jump to line 15. Because files change over time, line 15 might have shifted to line 20. `patch` reads the "context lines" (the unchanged text provided before and after the `+` and `-` changes). It searches the target file for a block of text matching these context lines.

If it finds an exact match at line 20, it applies the offset and injects the code. If the context doesn't match perfectly, it utilizes a "Fuzz Factor." It strips away the outermost context lines one by one (up to the `-F` limit) and searches again. If it ultimately fails to find a safe insertion point, the hunk is rejected. `patch` leaves the file partially modified (applying successful hunks) and writes the failed instructions to a `.rej` (reject) file.

## Performance Notes

- Applying patches is incredibly fast, bounded almost entirely by disk I/O to read the target file into memory and write out the temporary modified file before atomically renaming it.
- Heavy reliance on "fuzzing" (when the target file is vastly different from the patch origin) degrades performance, as the internal algorithm must perform expensive sliding-window string comparisons across the entire file to guess the correct injection offset.

## Security Notes

- **Directory Traversal Attacks:** A maliciously crafted `.patch` file can include target filenames like `../../../etc/shadow`. Historically, vulnerable versions of `patch` would blindly follow these relative paths and overwrite critical system files. Modern `patch` versions aggressively sanitize and reject absolute paths and parent-directory traversal attempts.
- **Arbitrary Code Execution via `.rej` files:** If a patch fails, `patch` writes a `.rej` file. If the patching process occurs inside a publicly accessible web directory, dropping a `config.php.rej` file containing plaintext source code might inadvertently expose sensitive application logic or database credentials to web scrapers.

## Common Mistakes

- **Forgetting the `-p` parameter:** Running `patch < fix.diff`. **Why it's wrong:** Patches generated by `git` include phantom directory structures like `a/src/main.c`. If you are already inside the `src` directory, `patch` will look for a folder named `a` and fail. You must define how many directory levels to strip (e.g., `-p1`).
- **Ignoring `.rej` files:** **Why it's wrong:** `patch` exits with a non-zero code if hunks are rejected, but it _still applies_ the hunks that succeeded. If a user ignores the error, the application is left in a fractured, half-patched state, virtually guaranteeing compilation failures or runtime crashes.
- **Reverse patching accidentally:** **Why it's wrong:** If you run `patch` against a file that already has the patch applied, `patch` intelligently detects the code is already there and asks: `Assume -R? [n]`. If an automated script presses `y`, it will silently uninstall the patch.

## Best Practices

- Universally execute `patch --dry-run` before mutating codebases, especially when applying third-party vendor patches to customized source trees, to identify rejecting hunks safely.
- When generating patches for distribution, always use `diff -u` (Unified format) rather than the default `diff` output. Unified diffs bundle robust context lines, allowing `patch` to calculate offsets mathematically even if the target file has been heavily mutated.
- In automated scripts, always capture the exit code (`$?`) of the `patch` command. If it returns `1` (partial rejection) or `2` (fatal error), the script must immediately abort the build pipeline to prevent deploying fractured code.

## Interview Questions

**Q:** What is the mathematical concept of "Fuzz" in the context of the `patch` command, and how does it prevent minor code variations from breaking a patch application?
**A:** "Fuzz" refers to the surrounding lines of unchanged text (context) bundled in a diff hunk. If a target file has been modified, the exact line numbers in the patch will be wrong. `patch` searches for the context lines to find the correct insertion point. If the context doesn't match perfectly, the engine applies a "fuzz factor": it ignores the outermost lines of context and tries matching the inner lines. This allows the patch to succeed even if minor changes were made near the target code.
**Q:** A developer generated a patch using `git diff > fix.patch`. You transfer this patch to an isolated server without Git, place it in the application's root directory, and run `patch < fix.patch`. It fails, complaining that it cannot find the file `a/app.py`. Why did it fail, and what flag fixes it?
**A:** `git diff` automatically prepends phantom directory labels (`a/` for the old file, `b/` for the new file) to all paths in its output. The `patch` utility interprets these literally and looks for a directory named `a`. To resolve this, you must pass the `-p1` flag (`patch -p1 < fix.patch`), which instructs the parser to strip exactly one leading directory slash from every file path before attempting the operation.
**Q:** What is the functional danger of executing the `patch` command inside a CI/CD pipeline without passing the `--forward` or `-f` flags?
**A:** If the CI/CD pipeline attempts to apply a patch that has already been applied, `patch` detects the reversed state and halts execution, throwing an interactive terminal prompt asking the user if they want to assume the `-R` (Reverse) flag. Because the pipeline is headless, it will hang indefinitely waiting for keyboard input. The `-f` (force) or `--forward` flags suppress these interactive prompts and force the command to fail cleanly.
