## What is it?

`terraform apply` is the execution engine of Terraform. It takes an execution plan—either generated dynamically on the fly or read from a pre-calculated binary plan file—and makes the necessary REST API calls to the targeted cloud providers to provision, update, or destroy real-world infrastructure. Upon completion, it updates the `terraform.tfstate` file to reflect the new reality of the managed resources.

## Why does it exist?

While `terraform plan` provides a safe, read-only preview of intended changes, a mechanism is required to actually enforce those changes on the cloud environment. `terraform apply` exists to translate the declarative Directed Acyclic Graph (DAG) of the execution plan into a sequence of imperative API requests. It handles complex parallel orchestration, respecting resource dependencies (e.g., creating a Virtual Network before creating a Subnet), managing transient API failures, and ensuring the local or remote state file remains perfectly synchronized with the cloud environment.

## Syntax

```bash
terraform apply [options] [plan_file]
```

## Flags

| Flag                  | Description                                                                                                             | Example                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `[plan_file]`         | (Positional) The path to a binary plan file generated by `terraform plan -out`. Executes exactly what was planned.      | `terraform apply tfplan.binary`            |
| `-auto-approve`       | Skips the interactive `yes/no` confirmation prompt. Essential for CI/CD pipeline automation.                            | `terraform apply -auto-approve`            |
| `-var="key=value"`    | Sets a variable dynamically. Ignored if a `[plan_file]` is provided, as variables are locked into the plan.             | `terraform apply -var="env=prod"`          |
| `-var-file=<path>`    | Loads variable values from a specified file. Ignored if a `[plan_file]` is provided.                                    | `terraform apply -var-file=prod.tfvars`    |
| `-target=<address>`   | Restricts the apply operation to a specific resource and its dependencies. Ignored if a `[plan_file]` is provided.      | `terraform apply -target=aws_instance.web` |
| `-parallelism=<n>`    | Limits the number of concurrent cloud API operations. Defaults to 10. Lowering this prevents API rate limiting.         | `terraform apply -parallelism=5`           |
| `-compact-warnings`   | Consolidates warning messages into a summary, making terminal output significantly easier to read on large deployments. | `terraform apply -compact-warnings`        |
| `-lock-timeout=<dur>` | Instructs Terraform to retry acquiring the state lock for a specified duration before failing (e.g., `5m`, `30s`).      | `terraform apply -lock-timeout=2m`         |

## Examples

```bash
terraform apply
```

> The standard interactive invocation. Terraform evaluates the code, runs an implicit `terraform plan` in memory, prints the proposed diff to the console, and halts. It prompts the user to type `yes` before proceeding with the actual API mutations.

```bash
terraform apply out.tfplan
```

> The production-grade invocation. It executes a pre-calculated binary plan file. Because the plan was explicitly locked in during the `terraform plan` phase, Terraform skips the interactive confirmation prompt and executes the API calls immediately.

```bash
terraform apply -auto-approve -var-file="dev.tfvars"
```

> A common pattern for ad-hoc sandbox deployments. It skips the `plan` phase entirely, evaluates the code against the `dev.tfvars` variables, and blindly provisions the infrastructure without asking for human confirmation.

```bash
terraform apply -parallelism=50 out.tfplan
```

> Forces Terraform to execute up to 50 resource API calls simultaneously. This drastically reduces execution time when deploying massive, horizontally scaled infrastructure (like 100 identical VMs), provided the cloud provider's API limits can handle the burst.

## Real-World Scenarios

**Continuous Deployment Pipelines**

```bash
terraform apply -auto-approve current-deployment.tfplan
```

> In a GitOps workflow, after a PR is merged to the `main` branch, a CD runner downloads the exact `.tfplan` artifact that was approved during the PR review. It executes `terraform apply` using that file. The `-auto-approve` flag ensures the runner doesn't hang indefinitely waiting for interactive terminal input.

**Mitigating Cloud API Rate Limits**

```bash
terraform apply -parallelism=1
```

> When working with highly restricted or slow legacy APIs (like specific on-premises VMware providers or small cloud accounts), the default parallelism of 10 causes `HTTP 429 Too Many Requests` errors, failing the deployment. An engineer uses `-parallelism=1` to force Terraform to provision resources strictly one at a time, bypassing the rate limits.

**Recovering from Stale Locks**

```bash
terraform apply -lock-timeout=5m out.tfplan
```

> In environments where multiple developers or pipelines might trigger deployments concurrently, state locking prevents corruption. Instead of failing instantly if another pipeline is running, `-lock-timeout=5m` tells the process to patiently poll the lock table for 5 minutes, proceeding automatically once the previous deployment releases the lock.

## When should it NOT be used?

- **Without a plan file in Production:** **Do not run a naked `terraform apply` in production.** Executing without a pre-calculated plan file introduces race conditions where the cloud state changes between human review and execution. Always use `terraform plan -out` followed by `terraform apply file`.
- **Data migration execution:** **Do not rely on Terraform for application data manipulation.** Terraform is designed for infrastructure control planes. If your deployment requires migrating database schemas or seeding data, use dedicated tools like Flyway or Liquibase after `terraform apply` completes.

## Alternatives

- **`terragrunt apply`:** **Best for multi-module orchestration.** A wrapper that can run `apply` across dozens of interdependent Terraform modules simultaneously using an `apply-all` paradigm.
- **Cloud Native IaC:** **AWS CloudFormation / Azure ARM Deployments.** Instead of Terraform's client-side orchestration, these services upload a template to the cloud provider, and the cloud provider's internal engine manages the apply execution logic.

## How it works internally

When you run `terraform apply tfplan`, Terraform bypasses the refresh and calculation phases because the execution graph is frozen inside the binary file.

Terraform acquires the state lock from the backend. It reads the Directed Acyclic Graph (DAG) from the plan file and begins a topological sort to identify resources with no dependencies. It initiates goroutines (up to the `-parallelism` limit) to execute the `Create`, `Update`, or `Delete` logic defined in the provider's Go code.

For a `Create` operation, Terraform sends a `POST` request to the cloud provider's API. It waits for a successful `200/201` response. Crucially, many cloud resources are asynchronous (e.g., an AWS RDS instance takes 10 minutes to boot). The Terraform provider contains retry and polling logic, continuously sending `GET` requests until the resource reaches a terminal `available` state.

Once a resource completes successfully, Terraform captures the resulting cloud-generated attributes (like the assigned IP address or ARN) and writes them into memory. It then traverses down the DAG, utilizing these newly generated attributes as inputs for dependent resources.

If any resource fails (e.g., due to insufficient cloud quotas), Terraform halts the execution of dependent resources but leaves successfully created resources intact. Finally, it serializes the in-memory state out to the backend `terraform.tfstate` file and releases the lock.

## Performance Notes

- **Asynchronous Polling Limits:** The total time `terraform apply` takes is almost entirely dependent on the cloud provider's provisioning speed. Terraform itself incurs minimal CPU overhead, as it spends 99% of its execution time blocking on HTTP API responses.
- **Parallelism Tuning:** Increasing `-parallelism` beyond the default 10 can speed up deployments of highly independent resources (like IAM roles), but causes severe diminishing returns and API throttling if the resources depend on shared control planes.

## Security Notes

- **Highly Privileged Execution:** `terraform apply` requires the highest level of credentials. The active environment (or CI runner) must possess the IAM privileges to create, modify, and destroy the core infrastructure components of your cloud environment.
- **State File Overwrites:** The apply process concludes by overwriting the remote state file. If the apply is killed forcefully (e.g., sending `SIGKILL` or unplugging a laptop), the remote state file might not be updated, leaving Terraform utterly unaware of the infrastructure it just successfully provisioned, requiring manual state imports to fix.

## Common Mistakes

- **Canceling a running apply with `Ctrl+C`**
  - _Mistake:_ Panicking mid-deployment and mashing `Ctrl+C` to stop it.
  - _Why:_ Sending a single `SIGINT` (one `Ctrl+C`) gracefully tells Terraform to stop creating new resources and wait for active API calls to finish, which is safe. Mashing it sends a `SIGKILL`, immediately terminating Terraform. This abandons the API calls, orphans the resources, corrupts the state file, and often leaves the remote state locked permanently, requiring a `terraform force-unlock`.
- **Passing `-var` when using a plan file**
  - _Mistake:_ Running `terraform apply tfplan -var="size=large"`.
  - _Why:_ You cannot change variables during an apply if you are using a binary plan file. The variables were baked into the plan during the `terraform plan` phase. Terraform will ignore the flag or throw an error.

## Best Practices

- **Always use `-auto-approve` with a plan file:** In CI/CD, `terraform apply out.tfplan` does not need `-auto-approve` because plan files never prompt for confirmation. Use `-auto-approve` only when performing ad-hoc sandbox deploys where you bypass the `plan` command entirely.
- **Persist the State File:** Ensure your backend (S3, GCS, Azure Blob) has Object Versioning enabled. If an `apply` corrupts the state or destroys critical resources, you can manually roll back the `.tfstate` file to the previous version in the storage bucket to restore visibility.

## Interview Questions

**Q: You execute `terraform apply` and halfway through, an AWS API error causes it to fail. Are the resources that successfully deployed before the error rolled back automatically?**
**A:** No. Terraform is not a transactional database. It does not perform automatic rollbacks. Resources that were successfully provisioned prior to the error remain active in the cloud environment, and Terraform will update the `terraform.tfstate` file to track those successful resources before exiting with the error code.

**Q: Why does running `terraform apply tfplan.binary` bypass the interactive `yes/no` confirmation prompt, whereas a standard `terraform apply` does not?**
**A:** The standard `terraform apply` implicitly performs a fresh plan calculation in memory. Because the user hasn't seen this plan yet, Terraform halts and demands a `yes` to ensure the user audits the proposed changes. When passing a binary plan file, Terraform assumes the file has already been audited and approved (often via CI/CD or previous manual review), so it safely skips the prompt to execute deterministically.

## Practice Problems

**Problem:** You have a generated execution plan saved as `deployment.tfplan`. Write the command to execute this plan, ensuring that Terraform uses up to 30 concurrent API calls to speed up the deployment.
**Hint:** Use the flag that alters the concurrent worker limit.
**Solution:**

```bash
terraform apply -parallelism=30 deployment.tfplan
```

**Problem:** You are running a script to spin up a temporary dev environment. You want to run `terraform apply` directly against your `.tf` files using `dev.tfvars`, and you want it to proceed without asking you to type "yes".
**Hint:** You need the auto-approval flag and the variable file flag.
**Solution:**

```bash
terraform apply -auto-approve -var-file="dev.tfvars"
```
