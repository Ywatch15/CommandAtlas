## What is it?

`az aks get-credentials` is an Azure CLI command that retrieves the Kubernetes configuration file (kubeconfig) for a specific Azure Kubernetes Service (AKS) cluster and securely merges it with the local client's configuration. It fetches the cluster's API server endpoint, the base64-encoded Certificate Authority (CA) data, and configures the `exec` authentication plugin required for Microsoft Entra ID (formerly Azure AD) integration. This fully automates the local setup required for the `kubectl` utility to authenticate and communicate with the AKS control plane.

## Why does it exist?

Kubernetes natively authenticates requests using X.509 client certificates, OIDC tokens, or static bearer tokens; it does not natively understand Azure's ARM (Azure Resource Manager) identity constructs. To bridge this gap, Azure requires an execution plugin (typically `kubelogin` or the Azure CLI itself) that dynamically converts an Azure identity into a valid Kubernetes bearer token. `az aks get-credentials` exists to abstract away the tedious, error-prone manual creation of YAML configuration files, automatically establishing this secure authentication bridge between the Azure control plane and the Kubernetes API server.

## Syntax

```bash
az aks get-credentials --resource-group <resource-group-name> --name <cluster-name> [options]
```

## Flags

| Flag                     | Description                                                                                                                      | Example                                            |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `-n`, `--name`           | Required. The name of the target Azure Kubernetes Service (AKS) cluster.                                                         | `az aks get-credentials -n prod-cluster`           |
| `-g`, `--resource-group` | Required. The name of the Azure Resource Group that contains the AKS cluster.                                                    | `az aks get-credentials -g rg-k8s-core`            |
| `-a`, `--admin`          | Retrieves the static cluster administrator kubeconfig instead of the default user (Microsoft Entra ID) kubeconfig.               | `az aks get-credentials -n cls -g rg -a`           |
| `-f`, `--file`           | Specifies a custom path to the kubeconfig file to write or update, instead of the default `~/.kube/config`.                      | `az aks get-credentials -f ~/.kube/custom`         |
| `--overwrite-existing`   | Silently overwrites an existing cluster configuration in the kubeconfig if a context with the same name already exists.          | `az aks get-credentials --overwrite-existing`      |
| `--context`              | Overrides the default context name generated by Azure (which is usually the cluster name) with a custom semantic name.           | `az aks get-credentials --context my-prod`         |
| `--credential-format`    | Defines the format of the returned credentials. `azure` relies on `kubelogin`, while `exec` uses standard client-go.             | `az aks get-credentials --credential-format azure` |
| `--public-fqdn`          | Forces the retrieval of the public Fully Qualified Domain Name (FQDN) for the API server on clusters equipped with Private Link. | `az aks get-credentials --public-fqdn`             |
| `--format`               | Formats the command execution output (e.g., `json`, `table`, `tsv`). Does not affect the generated YAML kubeconfig.              | `az aks get-credentials -o table`                  |
| `--subscription`         | Specifies the subscription ID or name containing the cluster, overriding the active CLI default subscription.                    | `az aks get-credentials --subscription 1234-5678`  |
| `--debug`                | Enables verbose logging, printing detailed information about HTTP requests, ARM API calls, and YAML merging operations.          | `az aks get-credentials --debug`                   |

## Examples

```bash
az aks get-credentials --resource-group rg-microservices --name dev-cluster
```

> Modifies the default `~/.kube/config` file to include the connection details for `dev-cluster`, automatically merging the new cluster, user, and context objects into the file, and sets the active `kubectl` context to this cluster.

```bash
az aks get-credentials -g rg-microservices -n dev-cluster -f ~/.kube/dev-config
```

> Writes the configuration to an isolated file rather than mutating the global default. To utilize this configuration afterward, the engineer must export the environment variable `export KUBECONFIG=~/.kube/dev-config` or pass `--kubeconfig` to `kubectl` commands.

```bash
az aks get-credentials -g rg-core -n prod-cluster --context prod
```

> Generates the configuration but overrides the default context name with the simple string `prod`. This allows developers to rapidly switch between clusters later using a memorable command like `kubectl config use-context prod`.

```bash
az aks get-credentials -g rg-core -n prod-cluster --admin
```

> Retrieves the "break-glass" static cluster administrator credentials. This bypasses Microsoft Entra ID entirely, utilizing an X.509 client certificate embedded in the kubeconfig that grants unrestricted `cluster-admin` privileges.

```bash
az aks get-credentials -g rg-core -n dev-cluster --credential-format azure
```

> Forces the kubeconfig's `exec` plugin block to use the `kubelogin` binary. This is the modern, highly recommended format that cleanly handles interactive browser logins, device code flows, and Managed Identity authentication for AKS.

## Real-World Scenarios

**CI/CD Pipeline Ephemeral Context Setup**

```bash
export KUBECONFIG=$PWD/kubeconfig
az aks get-credentials -g rg-apps -n staging-cluster
kubectl apply -k ./kustomize/overlays/staging
```

> In automated deployment pipelines (GitHub Actions, Azure DevOps), mutating the runner's global `~/.kube/config` can cause state corruption between parallel jobs. Pipelines export an ephemeral `KUBECONFIG` path scoped to the immediate workspace, run `get-credentials` to fetch the API endpoint, apply manifests, and allow the ephemeral file to be destroyed automatically when the job completes.

**Emergency Break-Glass Administration**

```bash
az aks get-credentials -g rg-prod -n critical-cluster --admin -f ~/.kube/admin-config
```

> If Microsoft Entra ID experiences a severe regional outage, or a misconfigured Kubernetes RBAC policy locks all users out of the cluster, administrators use the `--admin` flag. This downloads a statically signed X.509 client certificate that bypasses Entra ID and webhooks completely, allowing recovery of the cluster.

**Managing Multi-Tenant Clusters with Context Aliases**

```bash
az aks get-credentials -g rg-tenantA -n cluster-A --context tenantA
az aks get-credentials -g rg-tenantB -n cluster-B --context tenantB
```

> Platform engineers managing multiple isolated client environments use the `--context` flag to aggregate multiple AKS endpoints into their single `~/.kube/config` file under clean, semantic names. They can then seamlessly hot-swap their active terminal connection using `kubectl config use-context tenantA`.

## When should it NOT be used?

- **Inside Pods running in the cluster:** **Do not use this command inside a Kubernetes pod.** Pods must communicate with the Kubernetes API using natively mounted ServiceAccount tokens located at `/var/run/secrets/kubernetes.io/serviceaccount`. Running the Azure CLI inside a pod to fetch credentials is an anti-pattern and a severe security risk.
- **Managing non-AKS clusters:** **Do not use this for vanilla Kubernetes, GKE, or EKS clusters.** This command executes Azure-specific REST API calls (`listClusterUserCredentials`) against the Azure Resource Manager (ARM). It is entirely incompatible with non-Azure distributions.
- **Distributing kubeconfigs to teammates:** **Do not generate a kubeconfig and securely message it to a colleague.** The user kubeconfig file relies on the executor's local Azure CLI or `kubelogin` cache. Sharing the file only shares the endpoint and CA; the recipient must still possess the correct Azure permissions and run the command themselves to populate their own environment.

## Alternatives

- **Manual Kubeconfig Generation (Terraform):** **Best for strict infrastructure-as-code environments.** When provisioning an AKS cluster via Terraform (`azurerm_kubernetes_cluster`), the provider outputs the raw kubeconfig. You can use a `local_file` resource to write this output directly to disk, bypassing the Azure CLI entirely.
- **`kubelogin convert-kubeconfig`:** **Best for migrating legacy configs.** If you already have an older AKS kubeconfig that relies on the deprecated Azure CLI auth plugin, `kubelogin` can convert an existing file in-place without needing to reach out to the ARM API via `az aks get-credentials`.

## How it works internally

When `az aks get-credentials` is executed, the Azure CLI uses the active authentication profile to send a POST request to the Azure Resource Manager (ARM) REST API. The specific endpoint invoked is:
`https://management.azure.com/subscriptions/{subId}/resourceGroups/{rg}/providers/Microsoft.ContainerService/managedClusters/{name}/listClusterUserCredentials?api-version=...`

The AKS control plane authenticates the request using Azure RBAC. If the user possesses the `Microsoft.ContainerService/managedClusters/listClusterUserCredential/action` permission, ARM dynamically generates a base64-encoded YAML kubeconfig payload and returns it in the JSON response.

The Azure CLI decodes this base64 payload. It then reads the specified destination file (defaulting to `~/.kube/config`). Utilizing a safe YAML parser, it merges the returned configuration into the local file. It injects three primary objects:

1.  **Cluster:** The API server URL and the base64-encoded X.509 Certificate Authority data to prevent Man-in-the-Middle (MitM) attacks.
2.  **User:** An `exec` block. Rather than embedding a static password, this block instructs `kubectl` to execute a command (like `kubelogin get-token`) whenever an API request is made.
3.  **Context:** Maps the newly created User to the newly created Cluster.

Finally, the CLI rewrites the YAML file to disk with strict `0600` permissions and sets the `current-context` attribute to point to the newly merged cluster. During runtime, `kubectl` executes the `exec` block, which requests a fresh Entra ID access token, converts it into a format Kubernetes understands, and attaches it as a Bearer token to the Kubernetes API request.

## Performance Notes

- **API Latency:** The command executes synchronously and blocks while waiting for the ARM API to return the payload. Network latency to the Azure control plane dictates execution speed, which typically resolves in 1-3 seconds.
- **YAML Parsing Overhead:** If an engineer's `~/.kube/config` file has grown excessively large (containing hundreds of historical cluster contexts), the Python-based YAML parser inside the Azure CLI may consume noticeable CPU cycles to safely merge the new objects without corrupting the deeply nested structure.

## Security Notes

- **The Danger of `--admin`:** Using the `-a` or `--admin` flag downloads a highly privileged X.509 client certificate that bypasses Microsoft Entra ID completely. This certificate cannot easily be revoked without rotating the cluster's entire certificate authority. Access to the `listClusterAdminCredential` ARM action must be strictly guarded and audited.
- **File Permissions:** The generated `kubeconfig` contains sensitive infrastructure routing data and potentially cryptographic authority payloads. The Azure CLI ensures the file is written with restrictive permissions (`0600`). Administrators must ensure no automated backup tools inadvertently expose this file to wider network shares.
- **Local Credential Hijacking:** The standard user kubeconfig relies entirely on ambient Azure credentials. If a malicious actor can manipulate the `$PATH` to intercept the `kubelogin` or `az` binary execution within the `exec` block, they can theoretically steal the generated bearer tokens.

## Common Mistakes

- **"Unauthorized" after a successful command execution**
  - _Mistake:_ The command succeeds, but running `kubectl get pods` immediately returns `error: You must be logged in to the server (Unauthorized)`.
  - _Why:_ Successfully downloading the kubeconfig from ARM only proves you have Azure RBAC permissions to read cluster metadata. It does _not_ grant you access inside the cluster. Your Microsoft Entra ID user or group must still be explicitly bound to a Kubernetes `ClusterRole` via a `RoleBinding` (or AKS Local Accounts/Azure RBAC for Kubernetes) for the API server to authorize the request.
- **Missing `kubelogin` binary**
  - _Mistake:_ Running a `kubectl` command and getting an error about an unresolvable executable or plugin.
  - _Why:_ Modern AKS kubeconfigs generated with `--credential-format azure` rely on the `kubelogin` binary. `az aks get-credentials` does not install this binary. You must install it manually (e.g., `az aks install-cli` or `brew install Azure/kubelogin/kubelogin`).
- **Accidental Context Overwrites**
  - _Mistake:_ Running the command against two different clusters that happen to have the identical name but reside in different subscriptions, without realizing the context was silently overwritten locally.
  - _Why:_ The Azure CLI merges contexts based on string names. Always use the `--context` flag to enforce unique local naming if working across identically named Dev/Prod clusters in different tenants.

## Best Practices

- **Embrace Ephemeral Files for Automation:** In CI/CD or automation scripts, never mutate the global `~/.kube/config`. Always use `az aks get-credentials -f ./temp-kubeconfig` and export `KUBECONFIG=./temp-kubeconfig` to ensure a sterile execution environment that vanishes after execution.
- **Disable Local Accounts:** For maximum security, disable local accounts entirely on the AKS cluster during provisioning (`--disable-local-accounts`). This permanently disables the `--admin` flag and static X.509 certificates, forcing 100% of authentication to pass through auditable Microsoft Entra ID policies.
- **Leverage `kubelogin` for Managed Identities:** When running workloads on an Azure VM that needs to manage an AKS cluster, use the system-assigned Managed Identity. Generate the kubeconfig once, and ensure `kubelogin` is configured to use Managed Identity mode (`--login msi`), completely eliminating secrets from the authentication flow.

## Interview Questions

**Q: You run `az aks get-credentials`, but immediately afterward, `kubectl get nodes` returns "Unauthorized". Explain the architectural difference between the permission required to run the `az` command versus the `kubectl` command.**
**A:** `az aks get-credentials` requires an Azure Resource Manager (ARM) permission (`listClusterUserCredentials`) to download the metadata file. However, `kubectl get nodes` requires Kubernetes API data plane permissions. The Microsoft Entra ID token provided by `kubectl` must be mapped to a Kubernetes `ClusterRole` (via a `ClusterRoleBinding`) inside the cluster. Possessing ARM permissions does not automatically grant Kubernetes RBAC permissions.

**Q: What is the fundamental difference between the credentials downloaded when using the `--admin` flag versus the default command without it?**
**A:** The default command downloads an `exec` block configuration that dynamically negotiates short-lived tokens with Microsoft Entra ID (Azure AD), respecting Conditional Access and MFA. The `--admin` flag downloads a static X.509 client certificate signed by the cluster's CA that bypasses Entra ID completely, granting permanent `cluster-admin` privileges until the cluster certificates are manually rotated.

**Q: How does `kubectl` know how to acquire an Azure authentication token if Kubernetes doesn't natively support Azure AD?**
**A:** The `kubeconfig` file generated by this command contains an `exec` plugin block inside the `user` definition. When `kubectl` sends an API request, it reads this block and spawns a background process (usually running `kubelogin` or the Azure CLI). This process silently negotiates a token with Microsoft Entra ID, formats it, and passes it back to `kubectl`, which injects it as an HTTP Bearer token in the request header to the AKS API server.

## Practice Problems

**Problem:** You are managing an AKS cluster named `data-warehouse-prod` in the `rg-analytics` resource group. You need to download the kubeconfig, but you want to save it to an isolated file located at `/tmp/dw-config` to avoid altering your main setup.
**Hint:** Use the flag that specifies a custom path for the generated file.
**Solution:**

```bash
az aks get-credentials --resource-group rg-analytics --name data-warehouse-prod --file /tmp/dw-config
```

**Problem:** You are an administrator troubleshooting a locked-out cluster named `auth-cluster` in `rg-security`. You need to retrieve the break-glass cluster administrator credentials, but because you already have an old broken configuration with the same name, you need to ensure the CLI forcefully overwrites it.
**Hint:** Combine the flag that retrieves the static administrator certificates with the flag that permits destructive local file updates.
**Solution:**

```bash
az aks get-credentials --resource-group rg-security --name auth-cluster --admin --overwrite-existing
```
