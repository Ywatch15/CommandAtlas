## What is it?

`sar` (System Activity Reporter) is the primary reporting frontend for the `sysstat` package. It is an industry-standard performance monitoring tool that collects, reports, and saves a vast array of system metrics—including CPU utilization, memory paging, network traffic, block device I/O, and context switches. Uniquely, it functions both as a live polling tool and as a historical forensics analyzer, reading binary data files generated by its companion daemon (`sadc`) to retrospectively diagnose performance anomalies that occurred days or weeks in the past.

## Why does it exist?

Tools like `top`, `htop`, and `vmstat` are excellent for diagnosing performance issues occurring _right now_. However, when an alert fires at 3:00 AM indicating that a server crashed and recovered, live monitoring tools are useless because the event has passed. `sar` exists to provide continuous, lightweight telemetry archiving. By relying on a background daemon to quietly sample the kernel's `/proc` filesystem every 10 minutes and write the deltas to compact binary files, `sar` empowers system administrators to travel back in time, enabling definitive post-mortem analysis of memory leaks, I/O spikes, or network bottlenecks that occurred while they were asleep.

## Syntax

```bash
sar [options] [interval [count]]
```

## Flags

| Flag           | Description                                                                                                              | Example                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| `-u`           | (Default) Reports CPU utilization metrics (user, nice, system, iowait, steal, idle).                                     | `sar -u 1 3`                     |
| `-r`           | Reports memory utilization statistics, including free, used, cached, and buffer percentages.                             | `sar -r`                         |
| `-d`           | Reports activity for individual block devices (hard drives), detailing read/write sectors, IOPS, and average wait times. | `sar -d -p 1 3`                  |
| `-n <KEYWORD>` | Reports network statistics. Keywords include `DEV` (interfaces), `TCP`, `ERR` (errors), or `ALL`.                        | `sar -n DEV`                     |
| `-q`           | Reports queue length and load averages (1min, 5min, 15min), crucial for identifying system saturation.                   | `sar -q`                         |
| `-W`           | Reports swapping statistics (pages swapped in and out per second). High values indicate critical RAM exhaustion.         | `sar -W`                         |
| `-f <file>`    | Reads data from a specific historical daily binary data file (typically stored in `/var/log/sa/saDD`).                   | `sar -r -f /var/log/sa/sa15`     |
| `-o <file>`    | Extracts live metrics and saves them continuously to a specified file in binary format for later analysis.               | `sar -u 1 10 -o cpu_test.sa`     |
| `-s <time>`    | Sets the starting time (e.g., `08:00:00`) when reading from a historical file, isolating specific incident windows.      | `sar -u -s 14:30:00`             |
| `-e <time>`    | Sets the ending time (e.g., `15:00:00`) when reading from a historical file.                                             | `sar -q -s 02:00:00 -e 03:00:00` |

## Examples

```bash
sar 2 5
```

> The live polling pattern. It samples default CPU utilization metrics every `2` seconds, repeats this `5` times, and then prints an `Average:` calculation block at the bottom.

```bash
sar -r -f /var/log/sa/sa24
```

> The historical forensics pattern. It targets the binary log file for the 24th day of the current month (`-f sa24`) and extracts the memory utilization statistics (`-r`) for that entire 24-hour period, printing it sequentially.

```bash
sar -n DEV -s 02:00:00 -e 04:00:00
```

> Time-sliced network auditing. Extracts Network Interface (`DEV`) transmission and reception speeds specifically for the window between 2:00 AM and 4:00 AM today. This is the canonical method for investigating complaints about nightly backup jobs saturating the network link.

```bash
sar -d -p 1 3
```

> Live block device I/O troubleshooting. Polls every 1 second, 3 times. The `-p` (pretty-print) flag is absolutely crucial here; it translates raw kernel device identifiers (like `dev8-0`) into human-readable disk names (like `sda` or `nvme0n1`), showing exactly which drive is bottlenecking on IOPS (`tps`) or read/writes (`rkB/s`, `wkB/s`).

```bash
sar -q
```

> Extracts the historical run queue and load averages. If a server has 8 cores, a `runq-sz` (processes waiting for CPU time) consistently higher than 8 indicates severe CPU starvation.

## Real-World Scenarios

**Post-Mortem of an Out-Of-Memory (OOM) Crash**

```bash
sar -r -W -f /var/log/sa/sa10 -s 03:00:00 -e 04:00:00
```

> An application crashed at 3:45 AM on the 10th. The administrator reads the historical file (`sa10`) combining memory (`-r`) and swap (`-W`) flags. The output clearly shows the `%memused` creeping up to 99%, followed immediately by a massive spike in `pswpout/s` (pages swapped to disk). This definitively proves a memory leak caused swapping, which ground the server to a halt before the kernel OOM killer stepped in.

**Identifying I/O Wait Bottlenecks**

```bash
sar -u 1 10
# Note the %iowait column. If it's high (e.g., 40%), run:
sar -d -p 1 10
```

> A database query is running exceptionally slowly. The administrator checks the CPU usage and notices the `%iowait` is high, meaning the CPU is sitting idle, trapped waiting for the hard drive to return data. They pivot instantly to the disk metrics (`-d -p`), identify that `/dev/sdb` has an exceptionally high `await` (average wait time in milliseconds), proving the storage array is failing or undersized.

## When should it NOT be used?

- **Distributed Fleet Monitoring:** **Do not use `sar` for monitoring hundreds of servers.** `sar` is a localized, node-centric tool. If you manage an auto-scaling cloud fleet, you need centralized aggregation. Use node exporters (like Prometheus, Telegraf, or Datadog) to ship metrics to a centralized time-series database.
- **Sub-second micro-burst analysis:** The `sysstat` daemon typically polls every 10 minutes. Even if manually invoked (`sar 1`), its minimum resolution is 1 second. It physically cannot detect micro-bursts of traffic lasting 10 milliseconds that overwhelm NIC buffers. For that, you must use eBPF profiling or `ethtool` hardware counters.

## Alternatives

- **Prometheus / Grafana:** **Best for modern enterprise observability.** Replaces the `sysstat` cron job with a persistent `node_exporter` daemon, pushing metrics into a powerful TSDB for rich, visual dashboarding and alerting.
- **`dstat`:** **Best for real-time terminal correlation.** Replaces `sar`'s static tables with a dynamic, colorized stream that puts CPU, Network, and Disk I/O side-by-side on the exact same line, making it much easier to spot real-time correlations.
- **`vmstat` / `iostat`:** Native siblings to `sar`. They provide similar live outputs but completely lack `sar`'s historical data retention capabilities.

## How it works internally

`sar` relies on a split architecture: data collection and data reporting.

**Collection (`sadc`):** The `sysstat` package installs a cron job (typically in `/etc/cron.d/sysstat` or a systemd timer). Every 10 minutes, this timer executes `/usr/lib/sysstat/sadc` (System Activity Data Collector). `sadc` reads dozens of files from the `/proc` virtual filesystem (like `/proc/stat`, `/proc/meminfo`, `/proc/net/dev`). It computes the deltas since its last run and writes this raw, highly compressed binary data to a daily file in `/var/log/sa/saXX` (where XX is the day of the month).

**Reporting (`sar`):** When you execute `sar` from the terminal without live polling intervals, it opens today's `/var/log/sa/saXX` file. It parses the binary structs, applies the requested flag logic (e.g., `-u` for CPU calculations), formats the math into human-readable ASCII tables aligned by timestamp, and prints it to standard output.

Because `sar` stores data in day-of-the-month files (`sa01` to `sa31`), it maintains exactly one month of historical retention by default, silently overwriting last month's data on a rolling basis.

## Performance Notes

- **Negligible Overhead:** The `sadc` binary is written in C and is aggressively optimized. Running every 10 minutes to read `/proc` and append a few kilobytes to a binary file causes absolutely imperceptible CPU and I/O load, making it perfectly safe to leave running permanently on ultra-high-performance production databases.

## Security Notes

- **Data Exposure:** The `/var/log/sa/` directory is typically owned by `root:root`, but the binary `sa` files are often created with world-readable (`644`) permissions. Unprivileged users on a shared system can run `sar` and identify peak traffic times or memory usage signatures, which can be useful for side-channel reconnaissance during a penetration test.

## Common Mistakes

- **"Cannot open /var/log/sa/saXX: No such file or directory"**
  - _Mistake:_ Installing the `sysstat` package and immediately trying to run `sar`.
  - _Why:_ In Debian/Ubuntu, installing the package is not enough. You must edit `/etc/default/sysstat` and change `ENABLED="false"` to `"true"`, and then start the service. Until the `sadc` daemon runs, no historical files exist to read.
- **Forgetting the `-p` flag with disks**
  - _Mistake:_ Running `sar -d` to check disk I/O.
  - _Why:_ By default, `sar` outputs raw kernel major/minor device numbers (like `dev259-0`). Humans cannot read this. Always append `-p` (pretty-print) to force `sar` to resolve the device numbers into standard `/dev/nvme0n1` or `/dev/sda` names.
- **Misinterpreting CPU percentages**
  - _Mistake:_ Seeing `%usr` at 25% on a 4-core machine and thinking the app is barely using the server.
  - _Why:_ `sar -u` displays the _average_ across all CPUs. 25% on a 4-core machine means exactly one core is pinned at 100% capacity. If the application is single-threaded, it is maxed out. Always run `mpstat -P ALL` to verify per-core utilization.

## Best Practices

- **Change Data Retention:** By default, `sysstat` keeps 28 days of logs. If compliance requires more, edit `/etc/sysstat/sysstat` (or `/etc/sysconfig/sysstat` on RHEL) and change `HISTORY=28` to `HISTORY=365`. The binary files are tiny, so storing a year of telemetry costs negligible disk space.
- **Combine Flags for Correlation:** Do not run `sar -u` then `sar -r`. Run `sar -u -r -q 1 5` to stack the outputs. This allows you to visually correlate if a spike in the run queue (`-q`) coincides directly with a drop in free memory (`-r`).

## Interview Questions

**Q: You receive an alert that a server experienced high latency at 10:15 AM today. You run `sar -q -s 10:00:00 -e 10:30:00`. The output only shows entries for 10:00, 10:10, 10:20, and 10:30. Why is the data granularity limited to 10-minute intervals, and how could you change it?**
**A:** The granularity is limited by the execution frequency of the `sadc` data collector. By default, the `sysstat` cron job or systemd timer is configured to poll the `/proc` filesystem and write to the binary log file exactly once every 10 minutes. To increase granularity to 1-minute intervals, you must edit the system cron job (`/etc/cron.d/sysstat` or the systemd timer configuration) and change the execution interval from `*/10` to `* * * * *`.

**Q: In the output of `sar -u`, you notice the `%steal` column is consistently sitting at 30%. What does this metric indicate about the underlying infrastructure?**
**A:** The `%steal` metric represents "Steal Time." It is exclusively relevant in virtualized cloud environments (like AWS EC2 or VMware). It indicates the percentage of time that the virtual machine _wanted_ to execute CPU instructions, but the underlying physical hypervisor forcibly took the CPU core away to service a different, noisy-neighbor virtual machine. High steal time definitively proves the host hypervisor is overprovisioned, and the VM must be migrated or upsized.

## Practice Problems

**Problem:** A developer suspects the server's network connection was bottlenecking yesterday between 1 PM and 2 PM. Write the command to extract the historical network interface telemetry (`DEV`) for that specific 1-hour time slice from yesterday's log file (assume yesterday was the 14th).
**Hint:** Combine the network flag, the file extraction flag, and the start/end time flags.
**Solution:**

```bash
sar -n DEV -f /var/log/sa/sa14 -s 13:00:00 -e 14:00:00
```

**Problem:** You are monitoring a live server. You want to simultaneously check the CPU utilization and the Memory utilization. You want the command to poll the system every 3 seconds, generate 4 outputs, and then exit.
**Hint:** Include both metric flags, the interval integer, and the count integer.
**Solution:**

```bash
sar -u -r 3 4
```
