## What is it?

`iw` is the modern command-line configuration utility for wireless devices in Linux. Designed to replace the deprecated `iwconfig`, it provides deep, comprehensive access to wireless networking parameters, utilizing the `nl80211` Netlink interface to control AP capabilities, perform BSSID scans, manage mesh routing, and configure radio physics.

## Why does it exist?

The legacy `Wireless Extensions` (WEXT) framework and its associated `iwconfig` tool were designed in the early days of 802.11b and relied on rigid, complex `ioctl()` system calls. As wireless technology advanced (WPA2/3, 802.11n/ac/ax, mesh networks), WEXT could not scale. `iw` was created alongside the new `mac80211` subsystem and `nl80211` API. It exists to provide a modern, Netlink-based interface capable of controlling advanced wireless physics, virtual interfaces, and contemporary security protocols natively.

## Syntax

```bash
iw [OPTIONS] { dev | phy | reg } <name> <command>
```

## Flags

| Flag / Object                | Description                                                                               | Example                              |
| ---------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------ |
| `dev <interface>`            | Targets a specific logical wireless network interface (e.g., `wlan0`).                    | `iw dev wlan0 info`                  |
| `phy <name>`                 | Targets a specific physical wireless radio hardware device (e.g., `phy0`).                | `iw phy phy0 info`                   |
| `dev <iface> scan`           | Initiates an active or passive 802.11 scan and dumps discovered AP network data.          | `iw dev wlan0 scan`                  |
| `dev <iface> link`           | Displays the current connection status, signal strength, and bitrates of the active link. | `iw dev wlan0 link`                  |
| `dev <iface> set type`       | Changes the operating mode of the interface (e.g., `managed`, `monitor`, `ibss`).         | `iw dev wlan0 set type monitor`      |
| `dev <iface> set power_save` | Enables or disables the hardware radio power-saving mechanisms.                           | `iw dev wlan0 set power_save on`     |
| `event`                      | Streams wireless events generated by the kernel (like disconnections or auth failures).   | `iw event -t`                        |
| `reg get`                    | Outputs the current hardware regulatory domain (country code and allowed frequencies).    | `iw reg get`                         |
| `phy <name> set txpower`     | Manually configures the transmission power limit of the physical radio antenna.           | `iw phy phy0 set txpower fixed 2000` |
| `help`                       | Outputs the massive, comprehensive list of subcommands and configuration trees.           | `iw help`                            |

## Examples

```bash
iw dev
```

> This enumerates all logical wireless interfaces attached to the system, outputting their `phy` (hardware radio) assignments, interface names (e.g., `wlan0`), interface types (e.g., `managed`), and MAC addresses.

```bash
iw dev wlan0 link
```

> This checks the active connection state of the `wlan0` interface. If connected, it prints the connected BSSID, SSID name, current RX/TX bitrates, and accurate signal strength in dBm.

```bash
iw dev wlan0 scan | egrep "SSID|signal"
```

> This triggers the radio to scan the local airspace for broadcasting Access Points (APs). The output is massively verbose, so piping through `egrep` isolates the critical BSSID names and their associated signal strengths.

```bash
iw dev wlan0 set type monitor
```

> This transitions the interface from standard `managed` mode (client mode) into `monitor` mode. In monitor mode, the radio captures all 802.11 frames on the channel (including those not destined for the host), which is essential for packet sniffing via `tcpdump` or `wireshark`.

```bash
iw dev wlan0 set power_save off
```

> This disables hardware power management on the wireless chip. Servers or IoT devices experiencing sporadic latency spikes or dropped packets use this to prevent the Wi-Fi card from powering down its radio array during brief periods of inactivity.

## Real-World Scenarios

**Executing Wireless Penetration Testing**

```bash
ip link set wlan0 down
iw dev wlan0 set type monitor
ip link set wlan0 up
iw dev wlan0 set channel 6
```

> Security engineers performing Wi-Fi audits bring the interface down, switch its type to `monitor`, and lock it to a specific frequency (Channel 6) to begin passively intercepting 802.11 handshake frames or injecting deauthentication packets.

**Auditing Regulatory Domain Constraints**

```bash
iw reg get
```

> Drone operators and embedded hardware engineers must ensure their wireless radios comply with local FCC/CE radio laws. Running `reg get` reveals the actively enforced country code, ensuring the device is not illegally broadcasting on restricted radar frequencies (DFS).

**Debugging Latency on Wireless Links**

```bash
iw dev wlan0 station dump
```

> Network administrators managing a Linux-based Access Point (AP) use this command to dump live telemetry for every connected client (station). It exposes expected throughput, signal-to-noise ratios, and packet retry rates to isolate clients suffering from severe interference.

## When should it NOT be used?

- **Connecting to secure WPA2/WPA3 networks:** **Reason:** `iw` is a low-level tool that configures the hardware radio; it does _not_ possess the cryptographic supplicants required to negotiate WPA/WPA3 4-way handshakes. **Use instead:** `wpa_supplicant` or `nmcli`.
- **Managing general daily networking on a laptop:** **Reason:** Modifying interfaces directly with `iw` conflicts with desktop daemons like NetworkManager, leading to rapid disconnects as the tools fight over the interface state. **Use instead:** Desktop UI applets or `nmcli`.

## Alternatives

- **`nmcli` (NetworkManager):** The high-level manager. **Tradeoff:** `nmcli` easily connects to complex Enterprise networks and handles cryptography automatically, but entirely abstracts away raw radio controls like setting monitor mode or TX power limits.
- **`iwconfig`:** The legacy predecessor. **Tradeoff:** `iwconfig` uses familiar `ifconfig`-style syntax, but relies on deprecated kernel `ioctl` calls and structurally cannot support modern MAC80211 features (like mesh networking or multi-BSSID support).

## How it works internally

`iw` interacts with the Linux kernel entirely through **Netlink sockets**, specifically the `nl80211` interface which communicates with the `mac80211` and `cfg80211` kernel subsystems.

When you run `iw dev wlan0 scan`, the CLI constructs a structured binary Netlink message (`NL80211_CMD_TRIGGER_SCAN`) and dispatches it over the socket. The `cfg80211` subsystem receives this, translates it into the specific driver commands for the hardware (e.g., Intel `iwlwifi` or Atheros `ath9k`), and instructs the physical radio (`phy0`) to cycle through frequency channels and listen for Beacon and Probe Response frames.

Because `iw` uses Netlink rather than simple text scraping or static `ioctl` structs, it natively supports streaming asynchronous callbacks from the kernel. This is evident when using `iw event`, where the utility acts as a daemon, listening on the socket for real-time `NL80211` multicast broadcasts (like roams or disconnects) and printing them instantly without polling.

## Performance Notes

- Executing an active scan (`iw dev wlan0 scan`) forces the hardware radio to leave its current channel and iterate through all available 2.4GHz/5GHz frequencies. This interrupts active network traffic, introducing latency spikes of hundreds of milliseconds for active connections.
- Interfacing via Netlink sockets makes querying station statistics (`station dump`) virtually instantaneous and safe to run in rapid polling loops.

## Security Notes

- **Root Privileges:** Altering physical radio states (like raising TX power or enabling monitor mode) requires `CAP_NET_ADMIN` capabilities (`sudo`).
- **Monitor Mode Risks:** Placing a device in monitor mode exposes the kernel to arbitrary, malformed 802.11 management frames broadcasted by attackers. Historically, poorly written wireless drivers have suffered kernel panics or buffer overflows when parsing maliciously crafted probe requests.

## Common Mistakes

- **Trying to connect to WPA networks with `iw`:** Running `iw wlan0 connect MySSID`. **Why it's wrong:** The `connect` subcommand in `iw` only supports legacy open (unencrypted) or WEP networks. Modern WPA networks require external cryptographic exchanges. You must use `wpa_supplicant`.
- **Setting monitor mode while the link is up:** **Why it's wrong:** The kernel will reject the request with `Device or resource busy`. You must first unbind the interface from active usage by running `ip link set wlan0 down`.
- **Overriding TX power beyond physical/legal limits:** Running `iw phy phy0 set txpower fixed 5000`. **Why it's wrong:** The kernel cross-references your request against the regulatory domain (CRDA) and the hardware's physical maximum EEPROM limits. It will silently cap the power or reject the command.

## Best Practices

- When executing automation scripts against wireless hardware, query the physical radio capabilities via `iw phy phy0 info` before attempting configuration, as features like `AP` mode, `mesh_point`, or specific 5GHz channel support vary wildly between chipsets.
- Combine `iw event` with background logging scripts on IoT devices to maintain an auditable trail of exact kernel-level disassociation codes, which is vital for debugging unstable remote deployments.

## Interview Questions

- **Q:** Why did the Linux kernel community deprecate the `Wireless Extensions` (WEXT) interface and the `iwconfig` tool in favor of `mac80211` and the `iw` command?
  - **A:** WEXT relied on `ioctl()` system calls and rigid data structures designed during the 802.11b era. It could not easily scale to support complex modern features like mesh networking, multiple virtual BSSIDs on a single physical radio, or advanced 802.11ac/ax parameters. The new subsystem uses `nl80211` Netlink sockets, providing a flexible, extensible, and asynchronous messaging framework controlled entirely via the `iw` utility.
- **Q:** What is the critical step you must perform before you can use `iw` to transition a standard Wi-Fi interface into `monitor` mode for packet capture?
  - **A:** You must administratively disable the network interface first. The kernel prevents altering the fundamental operational type of a wireless interface while it is active. You execute `ip link set wlan0 down`, switch the mode via `iw dev wlan0 set type monitor`, and then bring it back up with `ip link set wlan0 up`.
- **Q:** You run an `iw dev wlan0 scan` and the SSH session to the server stutters and experiences high latency for a few seconds. Why does this happen?
  - **A:** To perform a complete environmental scan, the physical radio antenna must pause transmission on its currently associated channel, retune its frequency, and sequentially listen across all other 2.4GHz and 5GHz channels to capture broadcast beacons. This hardware retuning interrupts active traffic flow, causing queued packets and latency spikes.
