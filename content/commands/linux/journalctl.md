## What is it?

`journalctl` is a command-line utility used to query, filter, and display logs collected by `systemd-journald`. It provides a centralized interface for viewing messages generated by the kernel, the initrd, system services, and standard user applications.

## Why does it exist?

Historically, Linux logging relied on plain-text files scattered across `/var/log/` managed by daemons like `syslogd`, making cross-referencing and structured querying difficult. `journalctl` was introduced with `systemd` to provide a unified, indexed, binary logging system. This allows for rich metadata attachment (like PID, UID, SELinux context) and high-performance filtering by time, service, or boot ID, solving the fragmentation problem of legacy logging architectures.

## Syntax

```bash
journalctl [OPTIONS] [MATCHES...]
```

## Flags

| Flag              | Description                                                                         | Example                                    |
| ----------------- | ----------------------------------------------------------------------------------- | ------------------------------------------ |
| `-u, --unit=`     | Filters output to show only messages from a specific systemd unit.                  | `journalctl -u nginx.service`              |
| `-f, --follow`    | Tails the journal continuously, printing new entries as they are logged.            | `journalctl -f`                            |
| `-b, --boot=`     | Shows messages from a specific boot; defaults to current boot, `-1` for previous.   | `journalctl -b -1`                         |
| `--since=`        | Starts showing entries on or newer than the specified date/time.                    | `journalctl --since "1 hour ago"`          |
| `--until=`        | Stops showing entries on or older than the specified date/time.                     | `journalctl --until "2023-10-01 12:00:00"` |
| `-p, --priority=` | Filters output by message priorities or priority ranges (e.g., err, warning, info). | `journalctl -p err`                        |
| `-n, --lines=`    | Limits the number of journal entries shown from the end of the log.                 | `journalctl -n 100`                        |
| `-r, --reverse`   | Reverses the output so the newest log entries are displayed first.                  | `journalctl -r`                            |
| `-o, --output=`   | Controls the formatting of the journal entries (e.g., short, json, cat).            | `journalctl -o json-pretty`                |
| `-k, --dmesg`     | Filters output to show only kernel messages, bypassing user-space logs.             | `journalctl -k`                            |
| `-g, --grep=`     | Performs a regular expression search on the MESSAGE= field of entries.              | `journalctl -g "Failed password"`          |
| `--disk-usage`    | Shows the current total disk space consumed by all journal files.                   | `journalctl --disk-usage`                  |
| `--vacuum-time=`  | Reduces disk usage by securely deleting entries older than a specified time.        | `journalctl --vacuum-time=30d`             |

## Examples

```bash
journalctl -u sshd.service
```

> This queries the binary journal specifically for logs generated by the SSH daemon unit. It excludes kernel messages and logs from all other services, providing a clean view of authentication events.

```bash
journalctl -b -1 -p err
```

> This retrieves logs exclusively from the previous boot (`-b -1`) and filters them to only show messages with a priority of error or higher (`-p err`). It is essential for determining why a system crashed before its last restart.

```bash
journalctl -f -n 20
```

> This behaves exactly like `tail -f`, displaying the last 20 log entries and then keeping the terminal session open to stream new system messages in real-time as they arrive.

```bash
journalctl --since "2023-10-01 08:00:00" --until "1 hour ago"
```

> This filters the entire system journal based on a precise time window. It processes both exact timestamps and natural language parsing ("1 hour ago") to isolate events that occurred during a specific incident window.

```bash
journalctl _PID=1234 -o json-pretty
```

> This searches the journal using exact metadata matching (`_PID=1234`) and formats the output as human-readable JSON. This reveals the deep internal metadata systemd attaches to every log line, such as exact timestamps, UIDs, and capability bounds.

## Real-World Scenarios

**Investigating a crashed web server**:

```bash
journalctl -u nginx.service --since today -p err
```

When users report 502 Bad Gateway errors, you run this to isolate error-level logs specifically for Nginx from the current day, cutting through thousands of standard access logs to find the exact configuration or socket failure.

**Debugging kernel panics from a previous boot**:

```bash
journalctl -k -b -1
```

If a server unexpectedly reboots overnight, this command pulls the kernel ring buffer logs (`-k`) specifically from the run session just before the crash (`-b -1`), helping you identify out-of-memory (OOM) kills or failing hardware drivers.

**Shipping logs to an external SIEM**:

```bash
journalctl -u myapp.service -o json --follow
```

When building custom log aggregators, you pipe this command's output into tools like `jq` or a forwarding daemon. The `--follow` flag ensures a continuous stream, while `-o json` ensures the downstream parser receives perfectly structured, easily queryable objects.

## When should it NOT be used?

- **Systems lacking systemd**: If you are administering Alpine Linux (OpenRC) or a BSD variant, `systemd-journald` does not exist. You must use `tail -f /var/log/messages` or `dmesg` instead.
- **Applications that bypass syslog/journald**: Some software (like older Apache setups, custom Java applications, or Docker containers without the journald logging driver) write directly to their own custom `/var/log/app.log` flat files. Use `tail` or `grep` on those specific files.
- **Fleet-wide log aggregation queries**: `journalctl` is strictly a node-local tool. If you need to search logs across 50 servers simultaneously to trace a distributed microservice request, use a centralized logging stack like Elasticsearch (ELK), Loki, or Datadog.

## Alternatives

- **`tail` / `grep`**: The traditional text-file tools. Tradeoff: they work universally on all Unix-like systems and custom application logs, but they cannot natively filter by complex metadata (like boot ID) and require parsing unstructured text.
- **`dmesg`**: Specifically dedicated to reading the kernel ring buffer. Tradeoff: `dmesg` is instantly available and faster for checking hardware issues immediately after boot, but it does not persist data across reboots the way `journalctl -k -b` does.
- **`rsyslog` / `syslog-ng`**: Traditional logging daemons. Tradeoff: they are better suited for defining complex routing and filtering rules to push logs to remote servers out-of-the-box, though they lack the structured querying interface of `journalctl` on the local CLI.

## How it works internally

The `systemd-journald` daemon continuously captures standard output (stdout), standard error (stderr), syslog messages, and kernel logs via `/dev/kmsg` and `/dev/log`. As it receives these streams, it attaches contextual metadata (like SELinux contexts, process IDs, and user IDs) and writes them into a binary, hash-indexed file format.

These binary files are stored either in `/run/log/journal/` (volatile, held in RAM, lost on reboot) or `/var/log/journal/` (persistent, written to disk). Because it is an append-only binary format with hash-based indexing, querying by specific metadata (e.g., `_SYSTEMD_UNIT=ssh.service`) is an O(1) or O(log N) lookup. When `journalctl` is invoked, it memory-maps these binary files, resolves the indexes according to your matches, interleaves multiple journal files chronologically, and paginates the final output through a pager program (usually `less`). Exit codes return `0` on success (even if no entries match the filter) and non-zero on syntax errors or permission denials.

## Performance Notes

- Querying by indexed metadata fields (e.g., `-u nginx.service` or `_PID=1234`) is exceptionally fast regardless of journal size because the engine bypasses scanning the actual log payloads entirely.
- Full-text searching using `-g` (grep) is highly CPU-intensive and remarkably slow on multi-gigabyte journals because it forces sequential decompression and regex evaluation across every single binary entry.
- Log rotation parameters (`SystemMaxUse` in `journald.conf`) dictate query speed over time; heavily fragmented or massively overgrown binary journals will exponentially increase disk I/O latency during broad time-range queries.

## Security Notes

- **Access Control Restrictions**: By default, unprivileged users can only query and view their own user-space logs. Viewing system-wide daemon logs, kernel messages, or logs generated by other users requires root privileges or explicit membership in the `systemd-journal` or `adm` user groups.
- **Forward Secure Sealing (FSS)**: The journal supports cryptographic sealing via `journalctl --setup-keys`. This seals the logs periodically, ensuring that an attacker who compromises the system as root cannot retroactively alter or delete historical log entries without cryptographic detection.
- **Denial of Service via Disk Exhaustion**: If rate limiting (`RateLimitIntervalSec`) or maximum disk usage (`SystemMaxUse`) are improperly configured, aggressive logging from a compromised or failing service can fill the entire `/var` partition, bringing down the operating system.

## Common Mistakes

- **Running without filters on high-uptime servers**: Executing just `journalctl` without arguments on a server running for years will attempt to load millions of lines, causing the terminal to hang while it calculates pagination. Always bound queries with `-n`, `-e`, or `--since`.
- **Confusing priority numbers with names**: Using `-p 3` instead of `-p err`. While `3` technically works (it is the syslog integer for error), `-p err` or ranges like `-p "emerg..err"` are self-documenting in scripts and prevent off-by-one memory mistakes.
- **Forgetting the unit suffix**: Running `journalctl -u myapp` might return nothing if the unit is actually a timer or socket named `myapp.timer`. It is safer to use the full unit name or check `systemctl status` to confirm the exact string.

## Best Practices

- Use the `--no-pager` flag if you intend to pipe `journalctl` output into other shell utilities like `awk` or `grep`. This prevents interactive pager prompts from stalling your automated scripts.
- Verify persistent logging is enabled. Ensure the directory `/var/log/journal/` exists on your filesystem; if it doesn't, `systemd-journald` silently falls back to `/run/log/journal/`, meaning all logs vanish the moment the server is rebooted.
- Manually prune your journals using `sudo journalctl --vacuum-time=14d` if you notice disk space warnings. Better yet, enforce this automatically by setting `MaxRetentionSec=14day` in `/etc/systemd/journald.conf`.

## Interview Questions

**Q:** How do you view logs from the previous system boot, and under what circumstances might this command fail to return data?
**A:** You use `journalctl -b -1`. This command will fail to return data if persistent logging is not enabled (i.e., logs are only being written to the volatile `/run/log/journal/` directory instead of `/var/log/journal/`), meaning older boot logs were lost when the system restarted.

**Q:** What is the technical difference between filtering with `journalctl -u service_name` and `journalctl _PID=1234`?
**A:** The `-u` flag filters by the logical systemd unit name, capturing all logs from the main process and any child processes spawned by that service across its entire lifecycle. The `_PID` flag filters strictly by the specific OS Process ID, which is exact but ephemeral, meaning you will lose the log trail if the service restarts and receives a new PID.

**Q:** How would you output `journalctl` logs in a format suitable for ingestion by an external, automated log aggregator?
**A:** You would use the `-o json` or `-o json-pretty` flag. This bypasses the standard text formatting and outputs each log entry as a structured JSON object containing all indexed metadata fields (such as `_SYSTEMD_UNIT`, `PRIORITY`, and `MESSAGE`), making it trivial to parse programmatically.

## Practice Problems

**Problem:** Find all sshd logs from yesterday that have a priority of Warning or higher.
**Hint:** You need to combine the unit flag, the time boundary flags using natural language, and the priority filter flag.
**Solution:** `journalctl -u sshd.service --since yesterday --until today -p "emerg..warning"` (This filters for the exact sshd unit, scopes the timeframe strictly to yesterday, and limits the output to events marked as warning, error, critical, alert, or emergency.)

**Problem:** Display the last 50 lines of the system journal and continuously follow new messages to the screen as they happen.
**Hint:** You need to use the exact same two flags you would typically use with the standard `tail` command.
**Solution:** `journalctl -n 50 -f` (The `-n 50` flag instructs the engine to load exactly 50 lines from the end of the binary file, and `-f` keeps the file descriptor open to print new entries as they are committed.)
